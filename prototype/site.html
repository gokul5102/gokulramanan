Case study · 2026 · Server lead

Building a BWIC alert system from scratch

Internal sales teams and external clients get alerts about BWICs, which are bond auctions. I was the server lead for a new alert service, which I designed and launched from scratch.

The problem

Sales teams and clients rely on alerts to follow BWICs, so notification latency matters. An alert is only useful if it arrives quickly. The service needed lower latency, and it needed to evaluate far more alerts concurrently.

What I built

The service is a rule engine. It evaluates each alert separately, over AMPS, a messaging engine, so one complex alert can't slow down the rest.

Alerts support nested AND/OR filters, so a single alert can combine many conditions.

Alerts are evaluated in 30-second batch cycles. If several BWICs match an alert within one cycle, the user gets a single notification for all of them, not one per match. That keeps notifications useful instead of noisy.

The service runs as several instances and uses leader election. If the leader fails, another instance takes over automatically, so the service stays highly available.

The result

Within each cycle, notifications now go out with 33% lower latency. The engine also handles 2,000 concurrent alerts, four times what it could before.

How I worked

As server lead, I architected the service and took it through to launch. I built it with agentic AI-assisted development, using GitHub Copilot agents with custom instructions and skills.

Built with Java · Spring Boot · AMPS · GitHub Copilot

Case study · 2025 · Led the redesign

Redesigning a live bond data platform

This real-time streaming platform sends RFQs (requests for quote) and trades to internal sales teams and external clients, so they have the relevant bond data before they act. I redesigned it, and it now has much lower latency and handles far more volume.

The problem

Sales teams and clients use this data to decide what to do next, so it has to be current. The platform needed lower latency, and it needed to handle much higher volumes of RFQs and trades.

What I built

I rebuilt the data flow with reactive programming in Java, so RFQs and trades stream through the platform as they arrive.

People can filter by several fields, such as trader, client or bond (by ISIN), and pick more than one value in each. The platform then shows the union of the data for everything they picked.

A visibility policy decides what each person can see. For example, a salesperson can see data for all the clients they cover. The platform applies it as an intersection, so a view only ever contains data that person is allowed to see.

Using set operations for both kept filtering efficient at high volume.

The result

Users now get data with 75% lower latency, and the platform handles 10 times the volume it did before. The production rollout had zero downtime.

How I worked

I led the redesign, working with other engineers on the team. Before the rollout, we tested it end to end in our test environments. Then we moved users over in stages, after A/B testing. That's how we kept the rollout at zero downtime.

Built with Java · Spring Boot · Spring WebFlux · AMPS

Case study · 2026 · Led the root-cause analysis

Fixing BWIC alerts in production

Internal sales teams and external clients rely on BWIC alerts. In production, our alert service started sending repeated notifications for the same alert. It was a top-priority issue, and I led the root-cause analysis.

The problem

Sales teams and clients rely on alerts to follow BWICs. They were getting several notifications for the same alert, by email and in their feed, even when bonds were updating less often. It was rated top priority, so it needed to be found and fixed quickly.

What I fixed

I traced it with Splunk logs, AMPS health queries and the number of active subscriptions per alert. Then I matched the AMPS topic that holds every user's alert subscriptions against the alerts that were actually firing.

That showed where the duplicate and dormant subscriptions came from. When a standby pod took over as leader, the last 30-second evaluation batch carried over, so the alerts in that cycle fired twice. Each takeover left extra subscriptions behind.

I fixed the root cause in how the takeover handled the evaluation batch. I didn't delete any subscriptions by hand. Once the cause was fixed, the dormant ones closed in AMPS on their own.

The result

Active subscriptions fell from 2,172 to 45, a 98% drop, and alerting was back to normal. Each alert now sends one notification per cycle again.

How I worked

I led the root-cause analysis. Deleting the extra subscriptions would only have hidden the problem, so I looked for why they were being created. Once we fixed that, they stopped piling up.

Built with Java · Spring Boot · AMPS · Splunk · Kubernetes

Why our alerts fired twice after a failover

What happened when a standby took over, and how we found it.

The full story is in the Case study Fixing BWIC alerts in production.

What we saw

People were getting the same alert more than once, by email and in their feed. It happened even when there weren't many bond updates. It was a top-priority issue, and I led the investigation.

How we tracked it down

The Splunk logs came first, then AMPS: its health, and the number of active subscriptions on each alert. A few alerts had far more than they should have.

The real clue came from comparing two lists: every alert subscription in the AMPS topic, and the alerts that were actually firing. The gap between them showed the duplicates and the dormant ones.

The cause

The alert service runs with a leader pod and a standby pod. When the leader failed, the standby took over, but it carried over the last 30-second evaluation batch. So the alerts in that batch fired again, and each takeover left extra subscriptions behind.

The fix

We changed the failover so that alerts that had already fired were closed properly instead of being carried over. After that, the duplicate subscriptions stopped showing up in the AMPS alerts topic.

Now each alert sends at most one notification per 30-second cycle, and only if a BWIC matches it. A recurring alert just moves on to the next cycle.

Filtering live bond data with union and intersection

How multi-select filters and a visibility policy became two set operations.

The full story is in the Case study Redesigning a live bond data platform.

The setup

Sales teams and clients use this platform to watch RFQs and trades as they come in. The data streams through with Spring WebFlux, and the screen lets people filter it by trader, client or bond (ISIN).

Picking more than one value

Every filter allows multi-select. Pick two traders, or three clients, and the screen shows everything for all of them. That's a union: the data for each value, merged into one view.

Showing only what you're allowed to see

Not everyone can see everything. A salesperson sees data for the clients they cover, and nothing else. That's an intersection: of everything the filters picked, only the part that overlaps with what the visibility policy allows.

Why sets worked well

Thinking of both as set operations kept the filtering simple and fast, even as the volume grew to ten times what it was before.
